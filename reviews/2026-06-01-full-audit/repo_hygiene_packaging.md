# Findings

## 1. Confirmed defect: package entry point is not exercised by tests or scripts

The repository has a Julia package entry point, `src/SlenderConeRecoil.jl`, which defines `module SlenderConeRecoil` and includes every source file (`src/SlenderConeRecoil.jl:1-13`). The test runner does not load that module; it includes individual bead test files directly (`test/runtests.jl:3-11`), and each bead test includes source files by path rather than doing `using SlenderConeRecoil` (for example `test/test_bead5.jl:1-7` and `test/test_bead8.jl:1-9`). The figure script also bypasses the package module and includes every source file manually (`scripts/figures.jl:9-17`).

Impact: package loading, exports, duplicate include behavior, and `Pkg.test`-style usage can break while the current tests and scripts still pass. This also leaves the public API undefined in practice, even though source files contain exports (`src/expr.jl:5-6`, `src/inner.jl:15`, `src/outer.jl:18`, `src/pde.jl:15`). This is especially important if the north star is a reusable best-in-class package rather than a one-off reproduction.

## 2. Confirmed defect: README-visible PNG figures are not regenerated by the figure script

The README embeds PNG assets (`README.md:35`, `README.md:41`, `README.md:47`, `README.md:53`, `README.md:59`, `README.md:65`), and the repository tracks PNG/PDF pairs in `figures/`. However, `scripts/figures.jl` only writes PDFs (`scripts/figures.jl:49`, `scripts/figures.jl:74`, `scripts/figures.jl:124`, `scripts/figures.jl:201`, `scripts/figures.jl:220`, `scripts/figures.jl:290`, `scripts/figures.jl:312`). Running the documented command `julia --project scripts/figures.jl` (`README.md:71-73`) will not update the assets that GitHub renders in the README.

Impact: README images can silently drift from regenerated scientific figures. This is a reproducibility and reviewability problem for generated artifacts.

## 3. Risk: advertised Julia compatibility is not encoded in package metadata

The README says the project requires Julia 1.10+ (`README.md:67-70`), but the checked-in manifest was generated with Julia 1.12.5 (`Manifest.toml:3`). `Project.toml` has package compat entries for `DifferentialEquations` and `Plots` only (`Project.toml:10-12`); it does not declare a `julia` compat bound. The package compat entries are exact-looking single-version bounds (`Project.toml:11-12`), which may be intentional pinning, but that policy is not documented.

Impact: a user on the documented Julia 1.10+ range has no package-level compatibility contract, and future `Pkg` resolution behavior is unclear if the manifest is not used. This is a reproducibility risk, not a confirmed failure, because no Julia package operation was run for this review.

## 4. Risk: package identity looks scaffolded and incomplete

`Project.toml` declares `name = "SlenderConeRecoil"` and a patterned placeholder-like UUID, `a1b2c3d4-e5f6-7890-abcd-ef1234567890` (`Project.toml:1-3`), mirrored in the manifest package entry (`Manifest.toml:2183-2186`). The project file also lacks common package metadata such as `authors`, and it does not declare `[extras]`/`[targets]` for tests even though tests use `Test` (`test/runtests.jl:1`) and the source depends on package loading behavior.

Impact: this is not a syntax error, but it is packaging debt. A placeholder-looking UUID and incomplete test metadata will create friction if this becomes a registered, reusable Julia package.

## 5. Confirmed defect: Node/Playwright dependency locking is intentionally ignored

The repository tracks `package.json`, which depends on `playwright` via a semver range (`package.json:1-5`). A local `package-lock.json` exists and pins Playwright 1.58.2 (`package-lock.json:25-31`), but `.gitignore` excludes `package-lock.json` (`.gitignore:7-9`). That means new clones will not receive the lockfile for the paper-fetching tooling.

Impact: the headed Playwright paper-fetch workflow can change under `npm install`, which is avoidable friction for research reproducibility.

## 6. Risk: literature artifacts are local-only with no source manifest or checksums

The paper fetcher writes into `docs/papers` and uses a persistent browser profile (`scripts/fetch_papers.mjs:14-15`). The workflow is explicitly headed, VPN-dependent, and may require manual Cloudflare interaction (`scripts/fetch_papers.mjs:2-8`, `scripts/fetch_papers.mjs:279-286`, `scripts/fetch_papers.mjs:302-307`). `.gitignore` excludes downloaded PDFs, screenshots, and the browser profile (`.gitignore:11-14`).

Impact: ignoring licensed PDFs is reasonable, but the repository has no tracked manifest of expected papers, checksums, access notes, or "known missing" state beyond prose in `HANDOFF.md` (`HANDOFF.md:35`). This increases friction for ground-truth fidelity reviews and future literature-backed work.

## 7. Confirmed defect: handoff documentation is stale relative to the current test runner

`HANDOFF.md` says "`test/runtests.jl` only covers beads 1-4 (symbolic)" (`HANDOFF.md:35-37`). The actual runner includes tests for beads 1 through 8 (`test/runtests.jl:4-11`). This contradicts the current repository state.

Impact: stale handoff notes can cause agents to skip or mis-prioritize quality gates. The file is still referenced as required compaction-recovery reading in `AGENTS.md` (`AGENTS.md:41-45`), so stale content has workflow impact.

## 8. Risk: legacy agent planning docs remain prominent and partly conflict with current state

`SlenderConeRecoil_CLAUDE.md` still contains an old bead-by-bead implementation plan, including requirements such as "one concern per file, ~200 LOC max per file" (`SlenderConeRecoil_CLAUDE.md:15`) and a hard rule of "<=200 LOC per file" (`SlenderConeRecoil_CLAUDE.md:140-148`). The current script is 329 lines by `wc -l`, and `src/similarity.jl` is 213 lines. The same legacy plan describes visualization deliverables as PDFs only (`SlenderConeRecoil_CLAUDE.md:128-133`), while the README now depends on PNGs (`README.md:35-65`).

Impact: this is not a source defect, but it is repo hygiene debt. New agents may treat stale planning guidance as current architecture policy.

## 9. Risk: AGENTS.md duplicates Beads workflow rules and makes session-close semantics too broad

`AGENTS.md` now has a project-specific Beads quick reference (`AGENTS.md:97-105`) and also embeds the Beads integration block with overlapping rules (`AGENTS.md:131-149`). The embedded session completion section mandates pull, `bd dolt push`, `git push`, and "never stop before pushing" for all work sessions (`AGENTS.md:151-175`). That is reasonable for an orchestrating implementation agent, but it can conflict with read-only review-agent prompts that explicitly forbid mutating source or other reports.

Impact: workflow instructions are directionally useful, but the current wording does not distinguish orchestrator responsibilities from read-only subagent responsibilities. That increases the chance of accidental pushes or Beads writes during review-only work.

## 10. Risk: `.gitignore` is sparse for Julia development artifacts

The root `.gitignore` currently covers Beads/Dolt runtime files, Node/Playwright tooling, and paper downloads (`.gitignore:2-14`). It does not include common Julia/local development outputs such as coverage files, docs build output, local scratch output directories, benchmark output, or temporary generated data.

Impact: no stray Julia artifacts were found in this pass, so this is a preventive hygiene risk rather than a confirmed defect. It will matter more as the package grows tests, docs, benchmarks, and research data pipelines.

# Open Questions

- Is the intended package identity still `SlenderConeRecoil.jl`, or should it evolve toward a more general `SimilarityMethods.jl`-style package name?
- Should generated figures be tracked as both PDF and PNG, or should the script generate only one canonical artifact type and the docs consume that type?
- Should the repository track a lightweight `docs/papers/manifest.toml` or similar with expected papers, DOI/URL, access notes, and checksums for locally downloaded PDFs?
- Is GPLv3 in `LICENSE` the intended license for the future reusable package?
- Are exact compat entries for `DifferentialEquations` and `Plots` intentional pins, or should they become supported semver ranges with a tested Julia version matrix?
- Should `bd dolt push`/`git push` be mandatory only for orchestrators and implementation agents, with explicit read-only carve-outs for review subagents?
